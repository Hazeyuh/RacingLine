# RacingLine：卡丁车赛车线与圈速优化

本项目在当前文件夹持续开发，目标是把清晰赛道图片转换成米制赛道模型，使用 Fastest-lap 的卡丁车模型计算赛车线和圈速，并提供方便的车辆调参、结果比较和优化过程展示。本文记录已确定的方案、现有资料与开发顺序，供后续对话直接接续。

内容依次为技术路线、赛道输入与标定、数据格式、功能规划、实施顺序和当前进度。

## 运行基础示例

当前本地网页已支持南京引力聚宝山图像赛道与官方 Vendrell 赛道，采用 kart-6dof 模型，支持 200cc（4.8 kW）与 270cc（6.3 kW）预设，车重默认 100 kg、人重默认 70 kg，可分别修改并重新求解。现已加入 Honda GX200 / GX270 官方扭矩曲线近似模型，以及可调减速比、调速器转速与离合器接合转速。视频数据校准暂缓。界面支持实验存档、赛车线与速度着色、转速、输出功率、纵向加速度与控制曲线、按圈速回放、累计时间 delta 和真实 IPOPT 收敛曲线。

本机已建立 `.venv`。启动后打开 <http://127.0.0.1:8765>：

```sh
./tools/start.sh
```

新环境安装与编译（首次依赖编译需要几分钟）：

```sh
brew install gcc
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
PATH="$PWD/.venv/bin:$PATH" .venv/bin/python tools/build.py > runs/build.log 2>&1
./tools/start.sh
```

选择车辆并设置功率、车重、人重，再输入实验名称和网格点数，点击启动求解；完成后选择另一实验作为 delta 基准。负 delta 表示当前更快。不同网格的差异用于检查数值稳定性。每次参数、日志、车辆 XML、解 XML 和结果保存到 `runs/<实验 ID>/`，网页支持导出 JSON。

南京赛道已按两图主直道宽度传递比例，参考线约 642.93 m，主直道图像测量约 8.51 m。已提取比赛闭环与路肩、排除维修通道，生成并真实读取 XML，完成 200、500、1000 点求解。500 点为 44.125 s，1000 点为 44.107 s，差约 −0.018 s。尺寸来自模糊卫星图与示意图，仍属估算；动力学是上游默认车辆。标定页可修改端点，几何和赛车线支持叠加原图；改变端点后需重建赛道，旧实验保留原输入。逐轮目标值和约束误差已可显示，逐轮赛车线尚未从上游接口导出。实现说明见 [docs/implementation.md](docs/implementation.md)。

## 已确定的技术路线

计算内核采用 [Fastest-lap](https://github.com/juanmanzanero/fastest-lap)，优先使用其自带的卡丁车模型。该项目采用 C++17 内核和 Python API，卡丁车模型具有六个自由度，描述纵向、横向、垂向运动，以及偏航、俯仰和侧倾，并求解瞬态动力学。

图片处理、输入检查和展示流程参考 [F1TENTH Raceline Optimization](https://github.com/CL2-UWaterloo/Raceline-Optimization)。这是 TUM 项目的 fork，其中地图转换、几何检查和可视化 Notebook 值得参考。我们不运行两套优化器；在图片处理层与 Fastest-lap 之间实现明确的数据转换。

整体流程：

```text
卫星图比例尺 + 清晰赛道图
          ↓
标定、赛道边界提取、路肩标记、人工修正
          ↓
米制左右边界 + 参考线 + 左右可用宽度
          ↓
平滑、闭环与几何检查 → Fastest-lap XML
          ↓
卡丁车模型 + 最短圈速求解
          ↓
赛车线、速度、控制量、圈速、实验比较与回放
```

目前不以 Apex 为主架构，也不从头重写完整车辆动力学内核。TUM、Apex 和 Optimal Racing Line 保留为算法参考或后续对照。

## 现有赛道资料与标定设定

原始文件保留在 `赛道图片和卫星图对照/`：

| 文件 | 尺寸 | 用途 |
|---|---:|---|
| `卫星图对照.png` | 900 × 642 像素 | 实际尺寸标定、位置对照 |
| `赛道图.jpg` | 1000 × 707 像素 | 清晰赛道边界、弯道与路肩识别 |

图片对应南京引力卡丁车俱乐部聚宝山赛道。两张图片已查看。卫星图左下角有 **25 米**比例尺，用户确认该比例尺精确，两张图均为平面图，并明确要求按两图之间的等比例缩放关系处理。

采用用户指定的简洁标定方法：先测卫星图比例尺的像素长度，得到米/像素；再在卫星图测量主直道某一明确位置的赛道宽度，换算为实际米数；最后在清晰赛道图测量同位置、同一对边界的宽度，得到清晰赛道图的米/像素比例。然后直接在清晰赛道图上提取几何。

标定时保存比例尺端点、主直道测量端点、原始像素坐标、计算过程和最终比例，生成标定叠加图。测量方向应垂直于该处赛道。其他对应位置可用于核对，不应未经用户要求就改成复杂的非线性配准方案。若检查发现会实质影响结果的尺寸矛盾，记录具体差异再处理。

**可压路肩计入可行驶区域。** 提取边界时包含已识别的可压路肩，并单独保存路肩区域，以便后续调整规则。不要把缓冲区、轮胎墙或维修区一并当成可行驶区域。赛道图有维修区和出入口，需要从比赛闭环中区分；行驶方向、起终点和最终比赛路径应在检查图中明确。

## 中间数据和 Fastest-lap 输入

原始图片是我们的源资料，不直接交给圈速求解器。F1TENTH 原流程使用 PNG/PGM 图片与包含分辨率、原点等信息的 YAML；本项目可根据标定生成这些信息，不要求用户再提供 ROS 地图。

建议保留可编辑的中间几何：米制左右边界、参考线、沿参考线法线测量的左右可用宽度，以及路肩区域。CSV 用于检查和交换，JSON 用于保存标定和来源信息。坐标轴、单位、左右方向和闭环采样约定必须明确，并由导出适配层转换为 Fastest-lap 约定。

TUM/F1TENTH 常用 CSV 的四列为：

```csv
# x_m,y_m,w_tr_right_m,w_tr_left_m
```

这可作为一种中间导出格式，但 **Fastest-lap 最终读取的是赛道 XML，不能直接读取这份 CSV，也不能只改文件后缀**。

已核对 Fastest-lap 的 `Circuit_preprocessor` XML 读取代码：二维闭环格式要求相应属性，并包含弧长、参考线、左右边界、航向、曲率相关数据、左右宽度及其导数等，还读取头部、预处理选项和坐标转换元数据。具体字段与单位以实际拉取的版本及其有效样例为准。应优先使用上游预处理/导出能力；如自行导出，必须通过真实读取和求解验证，不能仅检查 XML 语法。

几何检查至少覆盖闭环接缝、连续点序、重复点、路径自交、边界与法线异常、宽度合理性、曲率连续性，以及赛车宽度和安全余量。平滑和重采样后应将边界与参考线叠加到原图检查，避免平滑把边界推到障碍物内。

## 计划功能

第一版优先完成本地可用的工作流：查看标定与几何叠加图、导入/修正赛道、选择卡丁车参数、启动求解、查看状态、查看赛车线与速度曲线，并保存每次实验的参数与结果。

车辆调参先围绕上游模型实际支持的参数展开，核对刚性后轴、轮胎、载荷转移等具体实现。六自由度名称本身不能证明模型已经充分处理卡丁车内侧后轮离地；在检查代码前不要宣称支持。首次跑通可使用上游默认卡丁车参数，明确它不是用户实际车辆的已校准模型。

展示规划包括原图与赛车线叠加、速度着色、刹车/加速区段、控制量曲线、估计圈速、实验结果对比及按圈速播放。现有项目的 Notebook 可作参考，但方便使用的界面需要自行开发，具体框架尚未确定。

“看迭代”分为两项：调参前后完整结果对比，以及求解器内部每轮状态回放。先实现实验比较，再检查 IPOPT 回调与 C++/Python 接口，保存中间轨迹、目标值和约束误差。中间迭代可能不满足约束，不能作为最终可执行赛车线；不要承诺圈速每轮单调改善。

## 本地环境与实施顺序

已读取本机配置：MacBook Air，Apple M5，10 核 CPU，24 GB 内存。计算主要依赖 CPU；现已在本机完成 AppleClang + gfortran 编译与默认模型验证。Vendrell 500 点求解约 13.2 秒，1000 点约 37.0 秒；1000 点进程峰值内存约 549 MB。首次依赖编译需要几分钟，详细记录见 `docs/benchmark.json`。

用户接受一定计算时间，希望不过分漫长。实施顺序如下：

1. 在当前项目下组织代码和数据，保留两张原始图片；拉取 Fastest-lap 到独立的上游目录并记录版本。避免把整个外部项目源码混进自己的业务模块。
2. 验证本机工具链和依赖，编译 Release 版本；运行自带赛道与卡丁车的粗网格样例，记录耗时、峰值内存、收敛状态和输出。先证明内核可用，再扩展复杂度。
3. 按既定比例尺与主直道宽度方法完成标定，交付标定图和可追溯的参数记录。
4. 提取含可压路肩的比赛赛道几何，区分维修区；生成边界/参考线检查图、米制数据和基本统计。
5. 转成 Fastest-lap XML，验证读取；用粗网格求解用户赛道，核对路线是否在可行驶范围内，再逐步细化。
6. 增加车辆配置、实验存档、结果比较和展示界面；随后实现求解过程记录与迭代回放。
7. 完善文档、可复现安装流程和必要验证，再整理发布。发布目标、仓库及部署方式尚未确定。
